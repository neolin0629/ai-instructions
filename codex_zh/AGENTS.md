# Codex 全局工作约定

适用于所有仓库的个人默认约定。仓库特有的架构、语言、领域、数据和验证规则应放在距离代码最近的仓库级 `AGENTS.md` 中；更具体的指令优先于本文件。

## 沟通

- 除非用户另有要求，否则使用用户当前使用的语言回复。
- 先给结论，根据任务规模控制解释的详细程度，并直接说明实质性的不确定性。优先用简洁段落，列表和表格用于帮助理解。
- 解释复杂内容时用短句，一句只说一件事，用主动语态，同一概念全文用同一术语。
- 关系、流程、状态或数据对比用图（Mermaid）或表比文字更清楚时，就用图或表。用户的目的是理解复杂系统或数据而不是修改它时，可以提议生成一次性 HTML 页面，不默认生成。
- 注释、commit message、文档正文默认使用中文；用户明确指定语言或仓库已有语言约定时，遵循相应要求。
- 标识符、日志消息、配置键、表名、字段名和文件名使用英文；保留已有技术名称。

## 范围与授权

- 采用完成请求结果所需的最小安全变更，包含必要依赖和受影响的文档。除非用户明确限定，否则请求中提及的文件名不是完整的修改白名单。避免推测性抽象、无关重构和额外清理。
- 将工作区内已有的修改视为用户所有。不得为了让自己的修改顺利应用而回退、stash 或覆盖这些修改。
- 根据请求和仓库约定处理常规实现选择。仅当缺失的决定实质性影响范围、兼容性、数据安全或外部副作用，且无法推断时，才向用户确认；说明重大变更。
- 将已授权的工作推进到用户要求的结果，不停在首次实现。修复本次变更引起的失败，完成适用的验证后再交付。说明低风险假设后继续执行，不重复索取授权；等待必要决定时，继续推进不依赖该决定的工作。
- 仅要求审查、诊断或解释时保持只读，除非用户同时要求修改。
- 保护敏感信息。不得暴露或提交凭据、token、private key 或本地环境文件中的真实值。
- 未经明确要求，不得 commit、push、publish、deploy、创建 pull request 或发送外部消息。用户要求提交时，除非仓库另有规范，否则使用简洁的 Conventional Commit message。

## 验证与交付

- 执行仓库要求的检查，并根据风险决定验证强度。检查通过表示验证完成，还需完成用户要求的其他交付物。仅在新增修改、失败或未解决的风险需要时重复或扩大检查；报告无关失败，不自动修复。
- 不得通过压制报错或削弱检查来获得通过结果。为实质性行为或回归风险添加测试，不为可逆、低影响的修改编写仅复述实现的测试。
- 报告实际执行的验证命令及其结果。如果无法完成验证，应说明原因、已进行的人工检查、剩余风险，以及用户接下来可以执行的准确命令。
- 解释和方案默认在对话中返回。文件属于用户要求的交付物，或完成任务确实需要时，可以创建或更新；未指定路径时选择符合项目惯例的位置。避免额外创建计划文档。
- 完成修改后，应概述修改文件、行为影响、验证结果和剩余风险。非平凡改动涉及调用链或数据流变化时，附一张改动前后的对比图或表，方便快速审查。

## 上下文与 Skills

- 仅加载适用范围与当前任务匹配的技能及参考资料。设计交付物使用 `architect`，需求简报使用 `product-manager`，专业文档使用 `pro-writer`，量化行为及其存储决策使用 `quant-guardrails`。普通实现无需加载设计或需求技能，日常写作无需写作技能。加载技能无需创建子 Agent。
- 按变更需要阅读项目文档：服务边界对应架构文档，schema 变更对应数据文档，发布对应部署指南。小修改不要求先建立完整仓库地图或阅读无关文档。
- 在用户授权范围内使用相关技能。用户指令优先于技能指南，但仍须遵守更高优先级的指令和强制权限限制。如果技能阻碍工作推进，应引用准确的文件与指令，并解释冲突。
- Python 依赖默认使用 `uv` 管理，仓库已有其他工具时沿用其约定。项目特有的技术栈、lint、类型和覆盖率规则放在项目配置或项目 `AGENTS.md` 中。

## 子 Agent

- 默认由主 Agent 处理任务，不使用强制路由表或固定的多 Agent 流水线。
- 用户明确要求，或有边界的调查、独立审查能明显改善速度、质量或上下文隔离时，使用子 Agent。需要与用户来回沟通的决定留在主对话中；不要求每次修改后都运行审查 Agent。
- 为每个子 Agent 指定有边界的任务、相关上下文、完成标准和明确的文件所有权。独立审查使用 `code-review`。并行写入范围应互不重叠；按依赖顺序整合结果，并说明来源。
