# 全局工作约定

子仓库特有的架构、领域、表结构、验证命令写在该仓库自己的 `CLAUDE.md` / `AGENTS.md` 里，更具体的指令优先于本文件。

## 沟通与语言

- 除非用户另有要求，否则使用用户当前使用的语言回复。
- 先给结论，根据任务规模控制解释的详细程度，直接说明实质性的不确定性。
- 解释复杂内容时用短句，一句只说一件事，用主动语态，同一概念全文用同一术语。
- 关系、流程、状态或数据对比用图（Mermaid）或表比文字更清楚时，就用图或表。用户的目的是理解复杂系统或数据而不是修改它时，可以提议生成一次性 HTML 页面，不默认生成。
- 注释、commit message、文档正文：**中文**。例外：已有英文约定的仓库（开源项目、对外协作）沿用其约定。
- 标识符、函数名、类名、日志消息、配置键、表名、字段名、文件名：**英文**（为了可 grep）。

## 范围与授权

- 优先采用满足要求的最小安全变更。仅修改用户要求的文件及其直接依赖；避免推测性抽象、无关重构和额外清理。
- 不得静默修改架构、依赖、凭据、数据路径、公共 API 或数据库 schema。如果缺失的选择会实质性改变行为或范围，应向用户确认。
- 将已授权的工作推进至完成。说明低风险假设后继续执行，不重复索取本次对话中已经获得的授权。如果需要用户决定，等待答复期间继续推进不依赖该决定的工作。
- 未经明确要求，不得 commit、push、publish、deploy、创建 pull request 或发送外部消息。需要 commit 时用简洁的 Conventional Commit 格式，除非仓库另有约定。
- 绝不输出或提交真实凭证、token、私钥，以及本地环境文件里的真实值。
- 工作区里未提交的改动归用户所有，必须保留 —— 不要为了让自己的改动干净落地而回退、stash 或覆盖它们。
- 只被要求审查、诊断、解释、汇报时保持只读，除非同时也要求了改动。

## 工作方法

- 改动跨多个文件、代码不熟悉或做法不明确时，先探索再动手；一句话能说清的 diff 直接改。
- 调查要限定范围。大范围的代码库探索交给子 Agent，让主上下文专注于当前任务。
- 修根因。不得通过压制报错、跳过或削弱测试、放宽检查来让它们通过。
- 同一个修复连续失败两次后停止打补丁：说明失败暴露了什么，然后换思路或向用户确认。
- Python：依赖用 `uv` 管理，不用 pip，除非仓库已在用其他工具。

## 验证与交付

- IMPORTANT：报告完成之前，先运行一个能给出通过 / 失败信号的检查 —— 仓库的测试、构建、lint、对比输出的脚本，或 UI 截图。修 bug 时，条件允许先写一个能复现问题的失败测试。
- 给证据，不给断言：列出实际运行的命令及其结果。如果无法完成验证，说明原因、已进行的人工检查、剩余风险，以及用户接下来可以执行的准确命令。
- 验证强度与风险相称。检查通过后即停止，除非新增修改、失败或未解决的风险需要进一步检查。报告与当前任务无关的失败，但不自动修复。
- 只有用户要求独立文档或给出路径时才创建文档。实现和修复任务授权范围内必要的源码修改及现有文档更新。
- 完成修改后，概述修改文件、行为影响、验证结果和剩余风险。非平凡改动涉及调用链或数据流变化时，附一张改动前后的对比图或表，方便快速审查。

## Skill 与子 Agent

- Skill 按需加载，使用 skill 不需要创建子 Agent。`product-manager`：需求、范围、spec。`architect`：设计与实施计划。`pro-writer`：专业文档（报告、白皮书、方案），日常写作无需技能。`quant-guardrails`：行情、因子、回测、实盘与存储选型。`python-bootstrap`（手动调用）：为项目落地 Python 规范。
- 默认由主 Agent 处理任务。子 Agent 用于上下文隔离（大范围调查、输出冗长的任务）或独立的第二意见；需要和用户来回沟通的任务不交给子 Agent。
- 完成非平凡或有风险的改动后，报告完成之前让 `code-review` 子 Agent 在全新上下文里审查 diff。影响正确性或既定需求的发现必须修复，其余视为可选。
- 每项委派任务应明确范围、相关上下文、约束和预期产出。不要并行编辑重叠文件；有依赖的阶段顺序执行，并说明每项重要结论的来源。

## 压缩上下文

压缩上下文时保留：用户的需求与决定、已修改文件列表、验证命令及其最新结果、未决问题。
